# Short-term refresh and signal timeline (2026-11-18)

The previous daily-only v2 ignored unfinished current-day bars and refreshed only on page/cache demand. Its first six results hid other qualified sectors. This change keeps the same technical strategy and authenticated research API, while adding an explicit intraday preview lifecycle.

- Existing `/cron/radar-live` producer queues short-term work after a successful Radar snapshot. A fresh-Radar cron tick also checks overdue short-term work. Both use the existing single-worker executor and memory/deadline guards. No viewer is needed, no new scheduler or paid service is created. Auxiliary failures do not fail Radar.
- The existing daily snapshot job queues post-close reconfirmation after 14:00, skipping automatic core-only recovery. Intraday and close snapshots use separate storage keys (`short_term:short-tech-v2:intraday` and `short_term:short-tech-v2`). No schema changes.
- Market-session mode follows the exchange calendar, 09:00–13:35 Taiwan time. Intraday uses incomplete day-K bars only when the upstream market timestamp is on the same session and no more than 20 minutes old. Fetch time alone is insufficient. Yahoo can be delayed; this is a ten-minute snapshot service, not tick streaming.
- Intraday events are labeled provisional and can disappear on the next calculation. They cannot freeze an earlier provisional price/reason or overwrite the close archive. Same-day provisional exits are not described as confirmed realized account profits.
- Intraday relative volume is normalized by the elapsed fraction of the 270-minute session (15-minute denominator floor). This is explicitly a linear time estimate, not actual completed daily volume; raw chart volume stays unchanged. Closed bars retain unmodified relative volume.
- The page polls every 30 seconds when visible (5 seconds while a job runs), checks again on returning from the background, and does not rerender an unchanged result or reload the page. Generation time, approximate next batch, per-symbol source time and provisional status are visible.
- Whole-market preselection now excludes unsupported emerging-market records. Deep coverage is interleaved across technical setups and sector groups, without forcing an entry or sector quota in displayed picks. All qualified detailed rows stay in the stored result; `sector=電子` or `sector=非電子` selects at most six without rescanning. Responses do not ship every candidate's charts.
- Report catalogue sector counts, detailed sector counts and qualified sector counts. If a sector has no qualifying stocks, show the true empty state.
- K-line details show an always-visible reverse-date signal timeline with date, action, reference price, original reason and stop/target at that time. Each new reason includes historical technical values where relevant. Old events keep their observed reasons; missing reasons are explicitly missing. Historical replay is distinct from current or provisional signals.

Entry: rising MA20 above MA60, price above MA20, volume-confirmed breakout or MA20 recovery, downside <=6%, reward/risk >=1.5. No institution net-buy or absolute volume/turnover minimum. Add: at least 1R profit, a new 10-bar high, relative volume >=1.25, bounded combined risk; once only, half initial model units. Reduce: target rejection, two successive closes below MA10, or MA10 loss with auxiliary selling; once, half remaining units. Exit: touch of the previously known trailing stop, gap reference at lower open, stop precedence. Future trailing changes apply next session. No actual account/order/LINE actions.

Validation covers provisional entry and retraction, elapsed-volume calculation, old source rejection, separate persistence, producer integration/failure isolation, sector filtering and browser polling/timeline. Existing Radar, snapshot memory, trade/holdings and UI checks remain. Synthetic market scenarios are isolated test inputs, never published as live results.

Deploy through the existing main auto-deploy service. Rollback by reverting this PR and deploying; no migration or destructive data action is required. Previous close snapshots remain available, with selection-version mismatch forcing a fresh calculation.
